# CLAUDE.md — Furn-APP AI Backend

## 1. Purpose

This repository contains the Python/FastAPI AI backend for Furn-APP, a furniture marketplace backed by Supabase.

The backend is not a replacement for the marketplace database. Its job is to provide a secure API and, later, AI capabilities such as:

- natural-language furniture search
- product recommendation
- product comparison
- clarification of ambiguous requirements
- room-image analysis and furniture recommendation
- seller/product alternatives when an ideal match does not exist

Supabase remains the source of truth for authentication, products, sellers, inventory, marketplace data, prices, and availability.

The AI layer must never invent products, prices, inventory, sellers, dimensions, or availability.

## 3. System Architecture

High-level architecture:

```text
Flutter Furn-APP
      |
      | HTTPS + Supabase JWT
      v
FastAPI AI Backend
      |
      | verified user identity / user JWT
      v
Supabase
  - Auth
  - PostgreSQL
  - PostgREST
  - RLS
  - Catalogue
  - Sellers
  - Inventory
  - Marketplace data
```

The normal-user authorization path must remain:

```text
Flutter
  -> sends Supabase access token
FastAPI
  -> validates/authenticates the token
FastAPI
  -> performs user-scoped database access
Supabase/PostgREST
  -> evaluates PostgreSQL RLS
```

Do not silently replace this flow with unrestricted `service_role` access for normal user operations.

Privileged credentials must not become a shortcut around authorization boundaries.

## 5. Catalogue Boundary

The catalogue layer deliberately separates upstream Supabase/PostgREST data from public API models.

Expected flow:

```text
Supabase/PostgREST response
        |
        v
upstream_models.py
        |
        v
transform.py
        |
        v
public models.py
        |
        v
FastAPI response to Flutter
```

Preserve this boundary.

Do not make Flutter depend directly on unstable/raw Supabase table shapes when a stable API model is appropriate.

Known schema-mapping work already included aliases such as:

- `width_cm`
- `height_cm`
- `depth_cm`
- `weight_kg`

and corrected attribute enrichment based on the real Supabase schema.

Before changing catalogue mappings, inspect the current upstream models, transformations, tests, and any live-verification evidence.

## 6. Security Model

Security is a first-class architectural constraint.

The project has already identified risk categories including:

- overly broad grants
- dangerous or ambiguous `FOR ALL` RLS policies
- seller-ownership and seller-state authorization
- child-table authorization gaps
- public catalogue exposure
- financial-data exposure
- `SECURITY DEFINER` helper exposure
- unsafe function execution grants
- future/default privilege behavior

Treat security SQL as production-impacting infrastructure, even when it is not yet deployed.

### Required rule

For security-sensitive changes:

1. inspect existing SQL, evidence, docs, and tests
2. identify the exact invariant being changed
3. change the smallest necessary surface
4. add or update a regression test
5. run the relevant local verification
6. report what changed and what did not change
7. stop before live execution unless the user explicitly authorizes it

## 7. Live-System Safety Rules

### Default mode: offline/local

Unless the user explicitly asks for a live operation, work locally.

Do not do any of the following merely because they would be convenient:

- execute SQL against Supabase
- apply a migration
- invoke a live acceptance script
- send network requests
- change production/staging data
- rotate secrets
- modify RLS on a live database
- use service-role credentials against a live project
- delete or mutate remote data
- deploy
- push or force-push Git branches
- merge
- commit

If a task can be completed by editing code, SQL, docs, tests, or fixtures locally, prefer that.

If the user explicitly requests a live action, first inspect the relevant preflight/verification logic and state exactly what is about to happen.

Never claim a live action succeeded unless its actual output was observed.

## 10. Testing and Quality Gates

The project uses `uv`, `pytest`, and `ruff`.

For ordinary Python changes, use the smallest relevant tests first, then broaden verification.

Typical final local gate:

```bash
uv sync --offline
uv run python -m pytest
uv run ruff check .
uv run ruff format --check .
git diff --check
```

For SQL/security work, also preserve the repository's SQL parsing checks and security-specific regression tests.

Do not report "all checks passed" unless all checks you name were actually run successfully.

If a check cannot be run, state that explicitly.

Do not weaken a test merely to make it pass.

A test change must preserve or improve its ability to detect the security or behavior regression it is intended to guard.

## 12. Phase 3.2C Invariants

When modifying Phase 3.2C, preserve these invariants unless the task explicitly changes them:

- all 19 `FOR ALL` dispositions must remain accounted for
- all 122 findings must remain accounted for
- reconciliation must work in both directions
- preflight must be rollback-only
- preflight must not commit
- core and preflight guard logic must remain intentionally synchronized
- no accidental Storage hardening may enter the core/preflight SQL
- no accidental default-ACL changes may enter the core/preflight SQL
- negative/mutation tests must detect weakening of critical policy predicates

For furnishing-policy regression protection, tests intentionally guard exact predicate behavior such as:

- owner predicates
- draft-state predicates
- open-state predicates
- address-ownership predicates
- required `AND` joins
- rejection of `AND` -> `OR`
- rejection of `OR TRUE`
- rejection of `1 = 1`
- rejection of unsafe terminal-state substitutions

Do not replace these with weak substring-only tests.

## 13. API Design Rules

Keep API behavior explicit and typed.

Prefer:

- strict request/response models
- deterministic transformation functions
- clear separation between upstream and public models
- dependency injection for gateways
- small router functions
- explicit error translation
- testable pure transformations

Avoid:

- leaking raw PostgREST responses directly to clients
- hidden global state
- business rules embedded in route handlers
- duplicated auth parsing
- accepting a client-supplied user ID as proof of identity
- service-role access for ordinary user reads/writes

## 14. AI Architecture — Planned, Not Yet the Main Implementation

The AI system will sit above the secured catalogue/API boundary.

Planned flow:

```text
User request
    |
    v
Requirement extraction
    |
    v
Structured search specification
    |
    +--> clarification when necessary
    |
    v
Hybrid retrieval
    - semantic search
    - keyword search
    - structured filters
    - availability
    |
    v
Candidate ranking
    |
    v
Suitability / compatibility checks
    |
    v
Explanation + real catalogue recommendations
```

Example structured requirement:

```json
{
  "category": "sofa",
  "style": "modern",
  "color": "beige",
  "preferred_width_cm": 220,
  "room_type": "living_room",
  "max_price": 30000
}
```

### AI source-of-truth rule

The model may infer preferences and rank products.

The model must not fabricate marketplace facts.

These must come from trusted application data:

- product IDs
- product names when presented as catalogue facts
- sellers
- images
- dimensions
- materials
- price
- stock
- availability

If no suitable product exists, return that reality and offer alternatives or an appropriate seller/advert path rather than inventing a match.

## 17. Working Style for Claude

When given a coding task:

1. inspect the relevant code and current Git diff
2. state the important finding briefly
3. implement the smallest correct solution
4. add/update tests when behavior changes
5. run targeted checks
6. run broader checks when appropriate
7. inspect the final diff
8. summarize exactly:
   - what changed
   - files changed
   - tests/checks run
   - results
   - remaining risks/blockers
   - whether any live action occurred

For long tasks, maintain progress in the repository rather than relying on memory alone.

Do not stop merely because the task is large. Work incrementally and preserve a clear state.

## 18. Definition of Done

A task is not done because code was written.

For a normal local code task, done means:

- requested behavior is implemented
- relevant tests pass
- lint passes
- formatting is correct
- diff is reviewed
- no unrelated changes were introduced
- status is reported accurately

For a security migration package, done locally means only:

- SQL is reviewable
- preflight exists where required
- verification exists
- regression tests protect important invariants
- parsing/lint/tests pass
- documentation matches behavior
- human review status is explicit

Local completion does not equal deployment approval.
